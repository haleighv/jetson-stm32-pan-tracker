# CAN fault injection, Nucleo <-> Jetson
# Captured: 2026-11-13
# Bus:      classic CAN, 1 Mbps, Nucleo FDCAN1 + Jetson mttcan (J17). CANable on the bus but
#           its driver isn't loaded (gs_usb not in this JetPack kernel), so it neither sends nor
#           ACKs: the Nucleo and the Jetson are the only active nodes.
# Summary:
#   A. Jetson can0 down, Nucleo sends:  Nucleo TEC 128, error passive, and stays there (an
#      error-passive node whose only error is a missing ACK doesn't count further). Jetson back
#      up: the pending frame goes through, TEC 127 (warning). TEC only drops on successful
#      transmissions, so receiving 2,000 frames afterwards left it at 127.
#   B. Nucleo PD1 (TX) unplugged at the transceiver, Jetson sending every 10 ms:
#      - Nucleo: one `can send` -> bit errors on every retry -> BUS OFF in milliseconds.
#        It keeps receiving (rx climbing) but can't ACK.
#      - Jetson: nobody ACKs its frames -> ERROR-PASSIVE, TEC 128, stays. Auto retransmission
#        resends the same frame back to back: ~435,620 bus errors in about a minute (first run).
#        TX queue fills behind the stuck frame; cangen gets ENOBUFS.
#      - The Nucleo receives each retransmission as a valid frame (an error-passive
#        transmitter's error flag is recessive): rx 781 -> 2193 during the fault. Duplicates.
#      - PD1 back in: Nucleo stays BUS OFF until reset (M_CAN needs software to clear INIT).
#        Jetson stays error passive until a node can ACK again, then recovers 1 per good frame.
#        `ip link set can0 down/up` does not reset mttcan's error counters.
#      - Seen only from the other node: with TX broken, the Nucleo itself looked healthy from
#        its own side (receiving, no TX errors) until it tried to send.
# Raw output follows.
